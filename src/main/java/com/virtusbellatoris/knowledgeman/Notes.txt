6. @NotBlank on the entity only validates when JPA tries to persist it to the database.
    By that point you're already deep in the service layer.
    @NotBlank on the DTO validates at the controller level —
    the moment the request comes in, before any service or database code runs.

    But for @NotBlank on DTO to actually trigger, you
    also need @Valid annotation on the controller method parameter:
    public User register(@Valid @RequestBody UserDTO userDTO)
    Without @Valid — the annotations are ignored even if they're on the DTO.

    So the full picture:
    •	@NotBlank on DTO + @Valid in controller → validates incoming request early
    •	@NotBlank on entity → last line of defense before database
    Both together give you two layers of protection. That's the correct approach.

7. Why protected UserDTO() {}:
    Jackson (the library that converts JSON to Java objects) needs
    an empty constructor to create the object first, then fill the fields.
    Without it, Jackson can't deserialize your JSON into UserDTO.

    For your other DTOs it worked because Jackson can sometimes
    use the parameterized constructor if it knows the parameter names —
    but it's not guaranteed. Empty constructor is safer.

    Actually for DTOs specifically — make it public not protected, since Jackson needs full access.

8. Why remove @Enumerated:
    @Enumerated tells JPA how to store an enum in the database. D
    TO never touches the database — so @Enumerated has no effect and
    doesn't belong there. The enum itself works fine without it in a DTO.

15. @Component:
    You already know @Service and @RestController — both tell Spring "manage this class, create it, inject it where needed."
    @Component is the generic parent annotation of all of these. @Service and @Controller are just @Component with extra meaning:
        @Component — generic Spring-managed class
        @Service — a component that contains business logic
        @Controller — a component that handles HTTP requests
    For JwtFilter — it's not a service, not a controller. It's a filter — a different kind of Spring-managed component. So you use the generic @Component.

16. UserDetailsService:
        This is a Spring Security interface with one method: loadUserByUsername(String username).
        Despite the name "username" — in your case it will load by email since that's your login identifier.
        Spring Security doesn't know anything about your User entity.
        It has its own user concept called UserDetails — an interface that represents
        an authenticated user. UserDetailsService is the bridge between your database and Spring Security.
        When a request comes in with a JWT token:
            Your JwtFilter extracts the email from the token
            Calls userDetailsService.loadUserByUsername(email)
            Spring Security gets a UserDetails object back
            Uses it to verify the user exists and check their role
        You need to implement this interface in your UserService or a separate class.
        It requires returning a UserDetails object — Spring provides a built-in implementation
        called User (confusingly same name as your entity) from org.springframework.security.core.userdetails.User.

    SecurityContext:
        Think of it as Spring Security's memory for the current request.
        It holds information about who is currently making this request — their identity and permissions.
        When your JwtFilter validates a token, it needs to tell Spring Security
        "this request belongs to this authenticated user." It does this by putting
        an Authentication object into the SecurityContext:
            SecurityContextHolder.getContext().setAuthentication(authentication);

        SecurityContextHolder — the container that holds the SecurityContext
        SecurityContext — holds the Authentication object
        Authentication — represents the authenticated user (who they are + their roles)

        After this line, Spring Security knows the request is authenticated and allows it through to the controller.
        If you never set this — Spring Security treats every request as anonymous and blocks protected endpoints.

17. doFilterInternal method with Key concepts explained:

    filterChain.doFilter(request, response) — every filter in Spring is part of a chain.
    When your filter is done, it must pass the request to the next filter.
    If you forget this line — the request stops and never reaches the controller.
    Calling it at step 2 means "I have nothing to do with this request, pass it along."
    Calling it at step 7 means "I've done my job, now pass it along."

    return after step 2 — exits the method immediately. Without return,
    the code would continue executing steps 3-6 even though there's no token. return is the exit door.

    SecurityContextHolder.getContext().getAuthentication() == null — before
    setting authentication, you check if it's already set. This prevents overwriting
    an authentication that was set by a previous filter in the chain.

    UsernamePasswordAuthenticationToken — despite the name suggesting username/password,
    this class is used for any kind of authentication in Spring Security. The three parameters are:
    the user, their credentials (null since JWT already proved identity), and their roles/permissions.

    userDetails.getAuthorities() — returns the user's roles as a list Spring Security understands.
    This is how Spring knows if someone is ADMIN or REGULAR when you later protect endpoints with role checks.

18. doFilterInternal method - The full flow in plain English:
        Request arrives
        ↓
        JwtFilter runs
        ↓
        Has Authorization header with Bearer token?
          NO → pass to next filter (Spring Security decides)
          YES → extract token
                ↓
                extract email from token
                ↓
                load user from database
                ↓
                token valid?
                  NO → don't set authentication (Spring Security blocks protected endpoints)
                  YES → set authentication in SecurityContext
                        ↓
                        pass to next filter → reaches controller

    The deeper understanding — how SecurityContextHolder works internally,
    what FilterChain actually does, how UsernamePasswordAuthenticationToken flows
    through Spring Security — comes with time and experience.
    You don't need to understand every library line to use it correctly.

22. Best practice in the industry:
    Separate DTOs for each operation. Each endpoint gets its own request/response DTO. No reusing DTOs across different operations.

    So you'd have:
    UserRegistrationDTO — for registration
    UserProfileUpdateDTO — for profile update (includes currentPassword)
    PasswordChangeDTO — for password change
    UserResponseDTO — what you send back (never expose hashedPassword)

    Why:
    Each operation has different required fields, different validation rules, different security concerns.
    Mixing them into one DTO creates confusion and forces you to make fields optional that should be mandatory,
    or mandatory that should be optional.
    For example password is mandatory for registration but irrelevant for profile update. If you reuse one DTO,
    you either always require it or always make it optional — neither is correct.

    Response DTOs too:
    Best practice also separates what you receive (request DTO) from what you return (response DTO).
    You never return your entity directly — you return a UserResponseDTO that only contains safe fields
    (no hashedPassword, no sensitive data).
    So for your project the clean solution is:

    Rename current UserDTO to UserRegistrationDTO
    Create UserProfileUpdateDTO with profile fields + currentPassword
    Keep PasswordChangeDTO for password change
    Create UserResponseDTO for what gets returned

    That's the benchmark. Whether you implement it fully now or later is up to you.
